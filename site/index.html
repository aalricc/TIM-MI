Self-healing recovery agent

Your service breaks at 3 a.m.
MI fixes it in seconds.

MI watches your service's health. When it goes bad, MI works out why, picks one repair, checks it is safe, runs it and confirms the service is healthy. If the repair fails, it tries again with what it just learned. Every repair that works makes the next one faster.

Runbooks don't run themselves.

Most "auto-remediation" is a fixed script tied to a fixed alert. It fixes the outage you predicted and does nothing about the one you didn't.

Paged again

Someone wakes up for a fix everyone already knows

Restore the backup, recreate the table, restart the service. Each step takes thirty seconds to do, and the incident still runs for an hour while someone gets online.

Scripts are brittle

Static playbooks miss new failure shapes

A playbook knows one symptom and one fix. When the symptom changes slightly, it either does nothing or does the wrong thing with full confidence.

"Fixed" isn't fixed

Green health checks that still drop writes

A repair that brings the endpoint back but loses data or rejects writes isn't a recovery. Your tools still count it as one.

One loop: diagnose, decide, verify, learn.

Every incident goes through the same audited loop. MI runs exactly one action per attempt, and an independent check confirms it worked before MI learns from it.

MI1 · WatchPolls deep health and new error logs every second.
MI2 · Gather evidenceHealth, DB status, integrity, the app's schema, recent logs, the backup catalog.
RAG3 · Look it upPulls the relevant SQLite docs and repair skills MI has learned.
LLM4 · WHYFinds the root cause and cites the exact evidence behind it.
MI5 · RememberMatches the incident to past ones. Repairs proven on similar incidents take the fast path.
LLM6 · HOWWrites a primary repair and 2–4 alternatives as concrete, executable actions.
JEV7 · DecideA separate decision model scores each candidate for usefulness and risk, then picks one.
MI8 · Gate · run · verifyAllowlist, schema and sandbox checks. One action. Independent health verification.
If verification fails: keep the context, feed back the tool error and the post-attempt state, and loop to step 5. MI never repeats a failed action, and an incident fixed by someone else is never credited to MI.

Gets measurably better with every incident.

MI only learns from repairs that were independently verified.

  • Reward reflects data loss. A repair scores 1 − rows lost / rows before, so MI learns the least-lossy fix, not just the first one that turns the check green.
  • Class memory. Similar incidents form a class. Once a repair has proven itself enough times in a class, MI replays it on the fast path, still through the decision model, the gate and the verifier.
  • Skills library. Winning repairs are written up as skills and fed back into retrieval for the next diagnosis.
  • Healthy is not enough. If the service is back but its data is not, MI keeps the incident open and tries another fix until the rows are back.
  • No hints, no cheat sheet. The prompts describe the evidence and the tool interface, nothing else. Which fix works is learned from outcomes, not hard-coded.

Autonomy with guard rails you can audit.

MI acts on production, so every safety rule lives in code and is checked by tests, not left to the model.

Allowlist

Four operations. Nothing else.

Backup restore, SQL on the app database, file replace within the sandbox, and service restart (only after a failed attempt). Anything else is rejected before it runs.

Sandbox

Paths can't escape

Every path is resolved and checked against the app root or sandbox at the gate, and again at execution time.

One action

No runaway changes

Exactly one action per attempt, always followed by independent verification. Retries re-check health first.

Honest health

"Healthy" means writes work

The deep check confirms integrity, the schema and a rolled-back test write, so a repair that silently breaks inserts can't pass.

Harness

Sensors around the agent

Runtime invariant sensors, KPI thresholds, call budgets and an LLM judge watch every decision in production.

Full trail

Every step on the record

Evidence, diagnosis, candidates, JEV scores and the verdict are kept in the event log and shown on the live dashboard.

Questions teams ask

Does the model just guess? What stops a bad repair?

The model proposes. It doesn't execute. A separate decision model scores the candidates, a code-level security gate checks schema, allowlist and paths, one action runs, and an independent verifier decides whether it worked. Only verified repairs are learned.

Will it learn the wrong lesson from a lucky fix?

Rewards are graded by data loss, the fast path requires a confidence bound over several verified successes, and an incident that recovers on its own between attempts is closed without crediting MI.

Is it tuned to the demo faults?

No. The prompts describe the evidence and the action interface only. Tests enforce that they name no fault and no preferred fix, and that a simulated fault leaves no trace MI can read.

What does it work with today?

A SQLite-backed HTTP service with a deep health endpoint, a log endpoint and a backup catalog. The loop, the gate and the learning are service-agnostic. New operations are added through a documented, test-checked procedure.
